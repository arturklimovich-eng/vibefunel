# Implementation Plan

Related: [REPOSITORY_AUDIT](./REPOSITORY_AUDIT.md) | [ARCHITECTURE](./ARCHITECTURE.md) | [SECURITY](./SECURITY.md)

Rules for every stage: small steps; after each stage run the verification commands and fix failures before moving on; no `any`, no `as unknown as`, no empty `catch`; no mocks that look like production; do not declare a stage done if its checks were not run (state which were not run and why). This file is updated after each stage.

## Verification commands (all stages)

```
pnpm lint
pnpm typecheck
pnpm test        # vitest
pnpm build
```

Prettier formatting is part of `lint`. Stage-specific checks are listed per stage.

## Stage 4: Payments

Scope: server `PaymentProvider` interface and Stripe test mode first; then Solidgate per the official SDK/API if it supports the needed flow.
Deliverables: `PaymentProvider` (`createCheckout`, `verifyWebhook`, `getPaymentStatus`); `StripeProvider`; webhook route with signature, amount, currency, product, project checks; idempotency by provider event id; failure/cancel states; `not configured` state; `SolidgateProvider` after confirming server verification in Solidgate docs.
Dependencies: Stage 3 (storage for payment records and idempotency).
Definition of done (CLAUDE.md): payment succeeds only through a server-confirmed flow; secrets do not reach the browser.
Stage 2 groundwork: the runtime holds `payments[screenId]`, which must be set only from server-confirmed status (the `confirmPayment` setter in the runtime context is unused until this stage); `payment_succeeded` is the only purchase path past a checkout or upsell screen; the only other allowed exit is one explicit `default` decline edge taken solely by a `skip` Button, and `always` / `answer_*` edges there are `payment_bypass` errors.
Extra verification: sandbox only; webhook tests with signed and tampered payloads and replays; grep client bundle for secret names. Solidgate: React 19 smoke test; confirm webhook/status verification in docs before implementing.

## Stage 6: Custom domains

Scope: tenant hostnames for published funnels. DNS ownership verification, Host-based resolution restricted to verified domains, a certificate-issuance gate for the proxy, studio UI, and an operator runbook. The platform never talks to Coolify or issues certificates itself.
Deliverables: `domains` table with RLS and a service-role-only status RPC (`supabase/migrations/20261030120000_domains.sql`); file-mode equivalent; `lib/hostname.ts` normaliser shared by form, API and middleware; `server/domains/verify.ts` (TXT challenge `_funnel-verify.<host>` = `funnel-verify=<token>`, CNAME/A routing report, resolver override `CUSTOM_DOMAIN_DNS_SERVERS`); studio API (`/api/funnels/[id]/domains`, `.../[domainId]`, `.../verify`) and panel; `proxy.ts` rewrite of `/` on custom hosts to `/d/[host]` with 404 for every other path except payments and health; Stripe return URLs on the custom host; `GET /api/domains/serve-check` for Caddy on-demand TLS; DEPLOYMENT runbook (Caddy proxy with on-demand TLS, Coolify API alternative).
Dependencies: Stage 3 (projects, publishing), Stage 5 (deployment).
Definition of done: a hostname cannot become verified without the TXT record; only one funnel serves a hostname; unverified or unknown hosts get 404; studio and API are unreachable on custom hosts; checkout started on a custom host returns to it; lint, typecheck, build pass; the TLS path is documented truthfully (not exercised here).
